# scoring — 프롬프트·작업 채점 코치 플러그인 설계

작성일: 2026-08-03
상태: 승인됨 (구현 계획 대기)

## 1. 배경과 목적

담당자가 그동안 대표에게 직접 해오던 리뷰 — 작업물에 점수를 매기고, 왜 그 점수인지 설명하고, 다음에 더 잘 쓰는 팁을 붙여주는 일 — 를 담당자 퇴사 후에도 이어가는 Claude Code 플러그인.

기존 리뷰 방식:

- 잘 쓴 프롬프트: 80~100점
- 디테일이 부족하거나 품질이 아쉬운 프롬프트: 60~80점
- 점수와 함께 **왜 그 점수인지** 설명
- 함께 리뷰할 때는 **사용 팁**을 덧붙임 (예: "역할을 명확히 부여하세요 — '너는 애플의 스티브 잡스이고…'")

플러그인은 이 세 가지(점수 · 근거 · 팁)를 모두 재현해야 한다.

### 성공 기준

1. 대표가 3개월 뒤에도 플러그인을 켜두고 있다 — 끄지 않았다
2. `/score-report`에서 항목별 점수가 우상향한다
3. 채점 기준을 바꾸고 싶을 때 담당자 없이도 마크다운 파일 하나만 고치면 된다

가장 큰 위험은 정확도가 아니라 **이탈**이다. 느리거나 시끄러우면 꺼진다. 설계 전반이 이 위험을 줄이는 쪽으로 기울어 있다.

## 2. 범위

### 채점 대상

| 대상 | 채점 경로 |
|---|---|
| 대표가 쓴 프롬프트 | 훅 자동 (얕게) + `/score` (깊게) |
| 대화 세션 전체 | `/score-session` |
| 대표가 쓴 문서·기획안 | `/score-doc <경로>` |

### 범위 밖 (명시적으로 제외)

- AI가 낸 결과물 자체의 채점
- 담당자의 과거 리뷰 기록에서 채점 기준을 역추출하는 작업 — 이번 버전의 rubric은 일반적인 프롬프트 엔지니어링 원칙 기반으로 작성한다. 개인화는 rubric 파일을 직접 수정하는 방식으로 나중에 언제든 가능하다.
- 팀 단위 집계, 원격 서버 전송, 대시보드 UI

## 3. 아키텍처

### 3.1 핵심 결정: 하이브리드 (훅=결정론적, 스킬=LLM)

훅에서는 LLM을 호출하지 않는다. 결정론적 휴리스틱으로만 채점한다.

검토한 대안:

| 안 | 내용 | 기각 사유 |
|---|---|---|
| 전부 LLM | 훅에서도 `claude -p` 서브프로세스로 실제 채점 | 프롬프트마다 3~10초 지연 + 매번 토큰 과금. Claude Code 훅 타임아웃(3초)과 충돌. 이탈 위험 최고 |
| 최소주의 | 훅 없이 스킬만 | 자동 채점이 사라짐. 명령어 존재를 잊으면 플러그인이 없는 것과 동일 |
| **하이브리드 (채택)** | 훅은 휴리스틱 게이트, 스킬은 LLM 정독 | 훅 지연 ~50ms, 추가 토큰 0. 정확도는 스킬이 담당 |

### 3.3 컴포넌트 계약

각 단위는 하나의 책임만 가지며 독립적으로 테스트 가능하다.

**`lib/heuristics.js`** — 순수 함수. 파일 I/O 없음, 전역 상태 없음.

```
score(promptText, weights) -> {
  dims: { role: 0..25, context: 0..25, format: 0..25, constraint: 0..25 },
  total: 0..100,
  weakest: "role" | "context" | "format" | "constraint"
}
```

`weakest`는 점수가 가장 낮은 항목이다. 동점이면 `role` → `context` → `format` → `constraint` 순으로 앞선 항목을 택한다 (기본기에 해당하는 순서).

의존: 없음. 채점 감각이 이 파일 하나에 담긴다. 가장 자주 수정될 파일이므로 격리한다.

**`lib/rubric.js`** — `rubrics/*.md`를 읽어 훅이 쓸 임계값·가중치를 뽑는다. 파일이 없으면 내장 기본값을 반환한다.

```
loadPromptConfig() -> { threshold: 75, weights: {...} }
```

의존: `fs`.

**`lib/ledger.js`** — JSONL 적재와 조회.

```
append(record) -> void      // 실패해도 예외를 던지지 않음
read({ sinceDays }) -> Record[]   // 손상된 줄은 건너뜀
```

의존: `fs`, `os`, `path`.

**`lib/config.js`** — on/off 및 사용자 설정 로드.

```
isEnabled() -> boolean      // SCORING_OFF=1 이면 false
```

의존: `process.env`, `fs`.

**`scripts/prompt-gate.js`** — 훅 진입점. 조율만 하고 채점 지식을 갖지 않는다.

의존: 위 lib 4개 전부.

**`scripts/report.js`** — ledger를 집계해 요약 객체를 만든다. `/score-report` 스킬이 호출한다.

```
summarize(records) -> { avg7, avg30, byDim, weakestDim, trend }
```

의존: `lib/ledger.js`.

### 3.4 의존성 정책

**외부 의존성 0개.** Node 내장 모듈만 사용한다. 대표의 PC에서 `npm install` 없이 동작해야 한다. 테스트도 `node --test` 내장 러너를 쓴다.

## 4. 훅 동작

### 4.1 흐름

```
stdin JSON 수신
  → config.isEnabled() 확인 (false면 즉시 exit 0)
  → 스킵 판단
  → heuristics.score()
  → total >= threshold ?
       YES → 출력 없음
       NO  → weakest 항목 1개에 대한 코칭 노트 출력
  → ledger.append()
  → exit 0
```

### 4.2 등록

`hooks/hooks.json`:

```json
{
  "hooks": {
    "UserPromptSubmit": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "node \"${CLAUDE_PLUGIN_ROOT}/scripts/prompt-gate.js\"",
            "timeout": 3000
          }
        ]
      }
    ]
  }
}
```

이 형태는 같은 환경의 bkit 플러그인에서 이미 동작이 확인된 패턴이다.

### 4.3 스킵 조건

다음은 채점하지 않고 조용히 통과시킨다. 대화의 리듬을 방해하지 않기 위함이다.

- `/`로 시작하는 슬래시 명령어
- 20자 미만
- 짧은 수긍·감사 표현 (`ㅇㅇ`, `응`, `고마워`, `ok`, `네` 등 — 목록은 `heuristics.js`에 상수로 둔다)

### 4.4 채점 항목

각 25점, 합계 100점. 임계값 기본 75점.

| 항목 | key | 잡아내는 신호 |
|---|---|---|
| 역할 · 페르소나 | `role` | "너는 ~이다", "~로서", "~전문가", "as a", 직함·인물 지정 |
| 맥락 · 배경 | `context` | 배경 서술, 목적("~하려고"), 대상 독자, 참조 파일·데이터 언급 |
| 출력 형식 | `format` | "표로", "N줄로", "JSON", 개수·길이 지정, 예시 제공 |
| 제약 · 예외 | `constraint` | "반드시", "~하지 마", "제외", 톤 지정, 금지사항 |

휴리스틱은 의도적으로 러프하다. 이 단계의 역할은 "무언가 빠졌다"를 감지하는 것이고, 정밀한 판단은 `/score`가 담당한다.

### 4.5 출력 형식

임계값 미만일 때만, **가장 낮은 한 항목만** 지적한다. 네 항목을 모두 나열하면 읽히지 않는다.

```
📊 62점 · 출력 형식이 비어 있어요
   지금 프롬프트엔 "어떤 모양으로 답해달라"가 없습니다.
   → 끝에 "표 3행으로, 각 행 40자 이내" 한 줄만 붙여도 확 올라갑니다.
```

### 4.6 컨텍스트 오염 방지

훅의 stdout은 사용자에게 표시되는 동시에 Claude의 컨텍스트에도 들어간다. 아무 처리 없이 두면 Claude가 매 턴 "점수가 낮으니 프롬프트를 다시 작성해 주세요"라고 반응해 원래 작업을 수행하지 않는다.

따라서 출력을 다음 취지의 지시문으로 감싼다:

> 아래는 사용자에게 표시되는 코칭 노트입니다. 답변에서 언급하지 말고, 사용자의 원래 요청을 그대로 수행하세요.

대표는 노트를 보고, Claude는 하던 일을 계속한다.

### 4.7 실패 안전성

훅 전체를 try/catch로 감싸고 **어떤 경우에도 `exit 0`** 을 반환한다.

| 상황 | 동작 |
|---|---|
| rubric 파일 없음 | 내장 기본값으로 진행 |
| ledger 쓰기 실패 (권한·디스크) | 무시하고 통과 |
| stdin JSON 파싱 실패 | 조용히 통과 |
| 예상하지 못한 예외 | 조용히 통과 |
| `SCORING_OFF=1` | 즉시 통과 |

채점 도구 때문에 대표의 작업이 멈추는 상황이 최악이다. 끌 수 있다는 사실을 알면 오히려 끄지 않는다.

## 5. 스킬

| 명령어 | 입력 | 출력 |
|---|---|---|
| `/score` | 직전 프롬프트 또는 인자로 준 텍스트 | 항목별 점수 + 총점 + 근거 + 팁 2~3개 + **고쳐 쓴 프롬프트 예시 1개** |
| `/score-session` | 현재 세션 대화 | 종합 점수 + 반복된 약점 |
| `/score-doc <경로>` | 문서 파일 | `rubrics/doc.md` 기준 항목별 점수 + 근거 + 개선안 |
| `/score-report` | 없음 | 최근 7일·30일 평균, 항목별 추세, 가장 자주 무너지는 항목 |

각 스킬은 해당 rubric 파일을 읽어 채점하고, 결과를 `source: "skill"`로 ledger에 기록한다.

### 5.1 `/score`의 개선 예시

`/score` 출력의 마지막에 **고쳐 쓴 프롬프트 전문**을 넣는다. 점수와 설명만 주면 대표가 "그래서 뭘 어떻게 고치라는 건지"를 다시 번역해야 한다. 완성본을 보여주면 그대로 복사해 쓸 수 있다. 담당자가 옆에서 "이렇게 쓰시면 됩니다"라고 하던 부분에 해당한다.

### 5.2 출력 톤

- 존댓말, 간결하게
- 잘한 것 먼저 → 아쉬운 것 → 구체적인 한 줄 개선안
- 점수는 항목별 막대 + 총점

## 6. 채점 기준 파일

`rubrics/prompt.md`가 채점 기준의 단일 출처다. 스킬은 이 파일을 읽어 채점하고, 훅은 여기서 임계값과 가중치만 뽑아 쓴다.

각 rubric 파일은 항목별 만점 기준, 감점 사유, 점수대별 서술(60~80 / 80~100 등)을 담는다.

`rubrics/tips.md`는 항목별 개선 팁 라이브러리다. 예를 들어 `role` 항목이 낮으면 여기서 역할 부여 관련 팁을 꺼내 쓴다. 담당자가 알려주던 팁들을 이후 계속 추가하는 자리이기도 하다.

**로직(JS)과 기준(마크다운)을 완전히 분리한다.** 나중에 기준을 바꿀 사람이 JS를 건드리지 않아도 되게 한다.

## 7. 데이터

### 7.1 저장 위치

`~/.claude/scoring/ledger.jsonl`

플러그인 디렉터리 **바깥**이다. 플러그인 캐시는 업데이트 시 교체되므로, 그 안에 두면 누적된 점수 기록이 사라진다.

### 7.2 레코드 형식

```json
{
  "ts": "2026-08-03T14:22:10Z",
  "kind": "prompt",
  "source": "hook",
  "total": 62,
  "dims": { "role": 18, "context": 20, "format": 6, "constraint": 18 },
  "len": 180,
  "session": "a3f8…"
}
```

- `kind`: `prompt` | `session` | `doc`
- `source`: `hook`(휴리스틱 자동) | `skill`(LLM 정독) — 리포트에서 두 값을 섞지 않는다

### 7.3 프라이버시

**프롬프트 원문은 저장하지 않는다.** 점수와 길이만 남긴다. 대표의 프롬프트에는 회사 내부 정보가 포함될 수 있고, 그것이 평문 파일로 수개월간 디스크에 쌓이는 구조는 만들지 않는다. 추세 분석에는 점수만으로 충분하다.

## 8. 테스트

`node --test` 내장 러너, 외부 의존성 없음.

| 파일 | 검증 내용 |
|---|---|
| `heuristics.test.js` | 좋은 프롬프트 / 나쁜 프롬프트 픽스처 각 6~8개에 대한 항목별 점수. 채점 감각이 여기 고정된다 |

| `ledger.test.js` | append → read 왕복, 손상된 줄 건너뛰기, 쓰기 실패 시 예외 미발생 |

`heuristics.test.js`가 가장 중요하다. 채점 기준을 조정할 때 이 픽스처가 회귀를 막는다.

## 9. 배포

Git 저장소를 marketplace로 등록하는 방식:

```
/plugin marketplace add <repo>

```

이후 기준을 수정하면 대표는 `/plugin update`만 하면 된다. 저장소가 없는 경우 폴더를 복사한 뒤 로컬 경로를 등록하는 방법도 README에 함께 적는다.
